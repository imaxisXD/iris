Iris's answer panel, rebuilt in GPUI

These are the findings of the first trial (the answer panel alone, 17 November). Every surface the Rune copy has has since been built; tools/report.py makes the page that sets them all beside the Swift app.

The verdict

All 22 states of the panel draw in GPUI and match the Swift app closely: the same paper, pen lines, pink marker behind Iris's words, struck-out words, brush lettering, keycaps, tape label, brush-stroke button, red-pen notes and shadow. Every state's paper is exactly as tall as Swift's, to the point. Text and marks land within half a point of Swift's.

The riso printing is the same Rust code the Rune port uses (ported from Swift seed for seed), so the screen dots, wobbles and bristles land where Swift puts them. GPUI handles the layout, the text (through the Mac's own text engine) and the pen lines as vector paths.

Live, on the test display

The live panel: a borderless floating panel that never brings Iris to the front; the app in front stayed in front through every click. Only the paper is drawn, and its shadow falls on what's underneath (shown here over dark grey).

Top: Fix. Bottom: Friendly, picked with a click. The draft waits 350 ms, then the answer lands.

A live window capture and GPUI's offscreen picture of the same state match on 99.6% of pixels. The only stronger difference is the 1-pixel window edge macOS draws, so the pictures below are what people would see.

The pink marker flying from Fix to Shorter, slowed 20 times so it could be caught mid-flight. It slides on the Swift panel's spring and stretches to the new word's width, as SwiftUI's matched move does.

What still differs

  • Half-point offsets: some small-caps labels and brush words sit up to half a point higher or lower than Swift's. The difference column shows them as outlines.
  • Key symbols (⌘ ↵ ⇥) are set in Menlo, as the Mac does for Swift; the ⌘ prints a touch heavier.
  • App icons are read from the app's icon file, so they print a touch more saturated than macOS's own rendering.
  • Not built yet: the flower that grows by your text and unrolls the panel, Replace and Quick Fix actually pasting, hover washes, the focus ring, the press squeeze, and the panel taking keys (Tab, 1–5, Return). The keys are wired, but testing them would mean the panel taking your keyboard, so they're untested.
  • The paper grain and the waiting dots are the same drawings caught at a different moment or offset, so the difference column shows them.

What GPUI did well, and where it pushed back

  • An offscreen renderer that uses the real Metal and the Mac's text engine. Every picture here was drawn that way, apart from the live captures, and it matches the live window.
  • Small and quick: half the size of the Rune build. Layout is boxes in rows and columns, text goes through the Mac's own text engine, and pen lines are drawn as vector paths.
  • Five snags, each worked around in our code with no change to GPUI:
    1. No variable-font axes. Iris's Martian Mono is a variable font set narrow and at a particular weight. GPUI can't set those axes, so the app ships three fixed cuts of it (renamed, as the font's licence asks).
    2. No letter spacing, so tracked labels are set one letter per cell.
    3. Nothing can be turned. GPUI can't rotate text or pictures, so the bits Iris sets a degree off straight (the tape, "looks good", the red-pen notes, the app icon) are printed whole as one picture from the font outlines.
    4. Windows that aren't in front run at 30 frames a second by default. Iris's panel is never in front, so it opts out.
    5. The floating panel takes the keyboard when it opens, even when told not to. The real Iris panel should take Tab and Return, so that's useful later. A test panel opened beside someone's work must not, so the test panel refuses the keyboard unless asked.
  • GPUI's last packaged release is a year old, so this pins today's Zed source. The first build downloads over 400 MB of it, and GPUI changes often, so moving to a newer version will sometimes mean fixing our code.
